# TAS 参考锚点对齐与 35D 状态升级方案

日期：2026-09-26。状态：协议与实机视觉测量已完成；profile 已标为 `verified`，正式训练默认 `tcp_protocol=anchor35` 与 `pot_visible_center_v1`。测量见 `runs/tas_anchor_calib_20260926/RESULT.md`。TAS 默认参考线是 `reference_trajectory_game_world.json`：游戏世界锅心，出生点锁到 `TransformPoint(b)`。旧地形拟合稿与 live-camera 中间稿保留。

## 1. 目标与设计决定

解决 TAS 视频的锅可见中心与游戏 Player Transform 原点不一致的问题，使在线奖励、离线重评分、评估和精英池使用相同的参考点。

第一版采用以下范围：

- 原始状态从 33D 增加到 35D；索引 0–32 的含义与顺序保持不变。
- 索引 33、34 为经标定的参考锚点世界坐标 `reference_anchor_x/y`，单位为游戏世界米。
- 游戏主线程使用真实身体 Transform 计算锚点，不使用 Python 朝向代理计算新采集数据。
- 基础动力学网络输入保持 39D；新增坐标先供路线比较使用，不同步增加模型输入特征。
- 动作、物理步长、落水条件、Teleport 的 Player 原点语义、接触几何和各空间通道的共同裁剪中心保持现有定义。
- 校正路线比较点会改变奖励和引导段切换，属于训练语义迁移；网络形状兼容不等于训练语义不变。
- 本次坐标改动不捆绑调整 σ、退火、PPO 参数、SIL 损失或 Pareto 容差。

## 2. 已确认的事实与尚缺信息

已确认：

- `PlayerStateService.SampleCurrentState()` 用 `playerTransform.position` 写入前两维。
- 当前视频检测点来自颜色轮廓质心与跟踪框融合；`pot_centre_calibration.json` 校正的是框与颜色中心，不是 Player 原点。
- 原生诊断归档中 PotCollider 与身体 Transform 位置重合，替换对象名称不能解决可见中心偏差。
- 当前 TAS JSON 没有身体姿态和输入动作，不能仅凭中心坐标唯一恢复 Player 原点；轨迹切线也不能替代身体角度。
- 当前 TCP 状态包不携带维度，Python 按 33 个 float 解包，不能直接更改服务器发送长度。

已测（2026-09-26，`live_dark_contour_v1`，独立 holdout n=15）：

- 实机可见锅心对应 Player 局部点 `b ≈ (0.066, -0.432)` m。
- Holdout 世界误差 median 0.013 m，P95 0.025 m；0.15 m 只是候选门槛，不是已声称精度。
- 相机正交配准误差 ≈ 0 px。身体转角约 ±15°，残差未见随角度系统漂移。
- TAS 金色检测不能用于实机：锅贴砂岩时与岩石并块。实机锅是深棕，不是 TAS 金锅。

尚缺：TAS 视频金锅中心与该 `b` 的转移误差、大角度翻滚、遮挡与不同相机尺度。这些数据不能用策略相对 TAS 的平均偏差代替。评审已接受实机深棕锅叠加图，profile 为 `verified`；残差与未覆盖姿态仍须单独报告。

## 3. 先完成锚点标定

### 3.1 采集同帧配对数据

新增标定脚本，复用原生诊断通道并补充必要的只读导出：

- 每份画面绑定物理采样序号、agent ID、Player 位置、身体旋转/缩放和相机投影参数。
- 渲染姿态与记录状态必须一致：控制刚体插值或在冻结物理后同步采样；只靠墙钟时间对齐不合格。
- 覆盖正常直立、左右倾斜、较大旋转、不同镜头位置/尺度，以及 TAS 对应的锅外观。
- 明确图像分辨率、裁剪/黑边与像素原点；Unity 屏幕坐标与图像行坐标转换只实现一份。
- 不用同轮多个完全相同复制体充当独立标定姿态。

### 3.2 检验固定局部锚点是否成立

对游戏截图执行与 TAS 一致的检测，拟合局部点 b，使原生身体变换与相机投影得到的像素位置接近检测位置：

`predicted_pixel_i = camera_i.project(body_transform_i.transform_point(b))`

使用稳健损失减小错检影响；按独立姿态/片段划分拟合与验证集。统计像素误差、换算到游戏平面的误差、偏差方向及其与角度/遮挡/外观的关系。

运行时锚点为 `Player.TransformPoint(b)` 的世界 x/y，完整处理旋转与缩放。世界坐标下的常数平移仅在多姿态验证支持时才可作为退化形式。

### 3.3 标定不通过时的处理

颜色质心受高光、遮挡与轮廓变化影响，未必对应固定身体点。若残差随姿态系统变化，则固定偏移方案不成立：先把视频提取升级为有明确物理定义的锅体关键点/姿态模板拟合，再输出同名锚点轨迹。

不把 Renderer.bounds 中心、碰撞体质心或子物体原点未经验证地声明为 TAS 检测中心。不通过标定时，可以完成协议工程，但不能把 35D 的两个数标记为已校准坐标并用于正式训练。

### 3.4 标定产物

新增版本化标定文件，包含 `anchor_id`、局部坐标、绑定的身体坐标系、单位、适用游戏/角色资产、检测器版本、相机条件、来源数据哈希、独立验证结果和有效范围。

保留旧参考文件，另存带显式锚点声明的新版本。只有验证证明既有中心符合锚点定义时才能沿用坐标；否则重提取，保留缺口和不确定帧，不在加载时偷偷修正旧 JSON。

建议把独立验证集 P95 误差不超过走廊半宽的 10% 作为上线候选目标；当前半宽 1.5 m 对应 0.15 m。该值是预设验收目标，不是已取得精度；相机配准和外部 TAS 视频的总定位误差必须另外报告。

## 4. C# 状态与 TCP 协议

### 4.1 状态采样

- `PlayerStateService` 或新建的锚点采样服务持有 Player Transform 与经校验的只读标定配置。
- `StepController` 保留基础 29D、cursor 4D 的分工，追加 anchor 2D；内部完整状态步幅为 35。
- 在与原状态相同的物理采样点收集锚点；Reset、NewSnapshot、Teleport、STEP 和其他返回状态的命令共用该入口。
- 锚点是身体位姿的派生量，不需要独立恢复到快照；Reset/Teleport 后立即从恢复后的 Transform 重算。
- 每个复制体绑定自己的 Transform；禁止使用 agent 0 的锚点填充所有 agent。
- 缺少标定、身体无效或坐标非有限时，新协议返回明确错误；不以零坐标或 Player 原点冒充已校准锚点。

### 4.2 显式协商与旧客户端兼容

新增 HELLO 命令。新服务器的每个连接初始处于 legacy33 模式，只有成功协商才进入 anchor35 模式。

HELLO 请求提出所需协议与状态 schema，以及期望的锚点和标定哈希。回复包含：

- 协议版本、状态 schema ID、原始维度、字段定义哈希；
- `anchor_id`、标定哈希、标定是否可用；
- agent 数、物理步长和每次 STEP 的物理帧数。

HELLO 采用带明确标记与长度的结构化回复；新客户端必须在有限超时内验证，遇到旧服务器普通回包或未知版本立即关闭连接。新参考任务不自动降级为 legacy33。

成功协商后的 v2 回复统一为带类型、载荷长度、采样序号的帧：状态与错误分开编码。状态载荷仍按 agent 交错保存 `[state:35×float32][done:1B]`，不改变动作含义。诊断回复使用相同序号关联；现有诊断 JSON 的版本号与状态协议版本分开命名。

没有协商的旧客户端仍收到原有 33D 包。注意内部数组步幅 35 与 legacy 发送步幅 33 不同：取 agent i 的数据时必须用内部步幅定位，再写前 33 维，否则从第二个 agent 开始错位。

协商处理只能读取已由主线程准备好的描述信息，不在 TCP 后台线程访问 Unity 对象。标定在一次连接/运行中保持不可变。

### 4.3 Python 接收

- `GoiEnv` 持有协商后的 schema，不再让一个模块级 `STATE_DIM=33` 决定全部收包长度。
- Reset/STEP/Teleport/配置类回复、诊断回包和错误分支全部按当前协议解析。
- 新协议校验类型、长度、agent 数、schema、序号和有限值，失败时停止该批采集，避免污染训练 buffer。
- 保留显式 legacy33 入口用于旧实验；兼容旧数据不代表允许新锚点任务缺失锚点。
- 实际 transport 维度以协商结果为准，不能被旧 checkpoint 中保存的 `config.state_dim=33` 覆盖。

## 5. Python 统一坐标入口

新增 `src/training/state_schema.py` 管理字段与 schema；新增 `src/training/reference_anchor.py` 管理路线比较点的选择和版本检查。

接口：`reference_position(raw_states, state_schema, reference_metadata)`

规则：

- 显式 legacy Player 原点任务读取 `[0:2]`。
- 校准锅锚点任务只读取匹配 schema 的 `[33:35]`。
- 校验参考文件、状态来源与标定的 `anchor_id`/哈希；不一致时明确报错。
- 旧 33D 不在该函数中偷偷回退或重建；重建必须先通过独立迁移步骤并记录来源。

所有生产入口调用同一函数：

- `rollout.py` 与 `experimental_rollout.py` 的 tracker 初始化；
- `reward.py` 的逐步 tracker 更新；
- `reference_corridor.py` 的离线 `replay_corridor_fields`；
- `local_evaluation.py` 的到达、保持与终点投影；
- 轨迹绘图、走廊诊断、参考回放和相关实验脚本。

Tracker 的二维几何核心可以保留；在外层提供 `tracker_from_state` / `step_state` 之类的共享入口，防止调用方继续写 `raw[:2]`。几何单元测试仍可直接使用显式二维点。

检查 `TrajectoryDataset` 的封顶行为描述子：走廊模式在 cap 对应状态上使用同一定义的参考位置；非走廊高度模式保留原定义。`(t,D)` 的算法无需因增加维度而改变，但其输入必须重算。

## 6. 模型输入与引导图

- `build_dynamics` 验证 33/35 schema 后按既有字段构建基础 39D 特征，不把 `state_dim` 当成网络输入维度。
- 为同一份前 33 维，35D 与 legacy33 生成的基础动力学特征应逐项一致。
- 接触几何、Player 中心裁剪和动作历史不因锚点追加而改变。
- 路线场仍在世界坐标系中构建。所有空间通道共享当前裁剪中心，不单独平移 wide 通道。
- 因锚点修正可能改变 tracker 段切换，wide 图选择会发生合法变化；在线采集与 SIL 离线重建必须在相同帧选择相同引导图。
- 如后续确有证据需要锚点特征，再单独实验新增 `anchor-player` 两维、39D→41D；第一版不合并此项。

## 7. 归档、精英池与 checkpoint 迁移

### 7.1 版本与指纹

状态归档、轨迹/精英池、评估 manifest、checkpoint 和缓存均记录：

- 状态 schema；
- 参考锚点 ID、标定哈希和来源类型（原生采集或经过验证的重建）；
- 原始参考路线哈希；
- 路线简化、半宽、置信权重、投影/跳变规则等会改变 credited 的配置与算法版本。

这些内容共同形成 reference fingerprint。只比较路线文件哈希不够，因为修改局部锚点即可改变 credited。指纹不一致的轨迹不能作为已经重评分的数据直接混入池。

旧文件缺元数据时，只能由确定的旧文件格式识别为 legacy，不能根据数组恰有 35 列猜出标定版本。

### 7.2 旧数据迁移

保留原文件，输出独立的新版本：

1. 有完整原始状态和对齐原生姿态：根据标定重建锚点，记录 reconstruction 来源。
2. 只有 33D：只有已验证的 `player→hub` 姿态代理在标定有效范围内满足误差要求时，才能用于带误差标记的迁移；否则保留旧口径，不能补零冒充新真值。
3. 只有剪枝轨迹：可以对保留片段重评分，但必须标为部分重评分。新口径下被删掉的尾段可能有新进度，不能声称恢复了完整 episode 的 D/t 或最优剪枝点。

从完整轨迹依次重算 credited、guidance_index、cap、剪枝、score、行为描述子、Pareto 点与池准入。不得把新锚点坐标与旧 `corridor_progress` 混用。

`--sil-seed` 与 `--sil-resume-pool` 必须执行指纹验证；旧字段存在不代表其仍有效。池快照保存/恢复也必须保留元数据并验证一致性。

### 7.3 权重迁移

第一版网络形状不变，可以复用 actor 权重。参考点指纹改变时，按新任务语义在新运行目录迁移：

- 丢弃旧 PPO rollout/buffer，不修改旧 on-policy 数据的奖励后继续更新；
- 重建路线相关缓存和输入历史；
- 触发现有 critic 预热流程，预热阶段保持 actor 不更新；
- 精英池必须先迁移通过，或从空池重新采集；
- 明确保存 σ 与其他无关参数的迁移决定，避免 `init-from` 的默认重置/退火偷偷混入坐标实验。

新旧得分不能直接横比。能够重评分的归档在同一新口径下比较；无法可靠迁移的部分单列。

## 9. 验证与验收

工程测试覆盖 33/35 编解码、HELLO 失败关闭、legacy 兼容、姿态变换、39D 特征一致、在线/离线 credited 一致、指纹冲突。视觉验收必须独立报告身体锚点误差、检测误差和镜头配准误差。实机深棕锅 profile 已 verified；仍不得宣称 TAS 视频金锅中心已经对齐。

修改 C# 后按项目 `build-plugin` 流程使用 VS2019 MSBuild 编译；PostBuild 自动部署 DLL，重启对应测试游戏后验证。构建/重启安排在自有测试运行边界，不中断无关训练。Python 测试与迁移脚本使用 `getting-over-it-analysis` 环境。

## 10. 实施顺序与完成标准

1. 保存现有协议/配置/参考指纹，建立同帧标定数据并验证锚点定义。
2. 固定通过验证的 anchor profile；必要时生成新 TAS 参考文件。
3. 实现 35D 采样、协议协商及旧客户端兼容，先通过编解码与实机采集验证。
4. 接通统一参考点入口、39D 特征兼容和完整元数据，验证在线/离线一致性。
5. 迁移可可靠重建的完整旧轨迹，重算精英池；其余资料保留 legacy 或部分迁移标记。
6. 在新运行目录加载权重，重建历史/缓存、预热 critic，完成有限烟雾验证。

完成条件：新采集的每份状态可追溯锚点定义；所有路线计算读同一锚点；协议与旧资料不会静默混用；标定有独立验证证据；旧权重可在新语义下完成采集、归档与更新。

如果视觉标定不通过，则完成状态只能报告为“协议/工程就绪，锚点标定未通过”，不能宣称已修复 TAS 与训练的中心误差。
